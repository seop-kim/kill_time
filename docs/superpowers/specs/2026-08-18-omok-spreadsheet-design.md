# 오목 (스프레드시트 위장) 설계 문서

- 날짜: 2026-08-18
- 상태: 승인됨, 구현 진행

## 범위

킬타임 프로젝트의 첫 게임으로 **오목**을 만든다. 숫자야구, 장기는 이후 이 게임에서 다지는
실시간 방/동기화 기반을 재사용해 별도로 설계·구현한다.

## 컨셉

업무 중에도 티가 나지 않도록, 전체 화면이 **Excel Online 스타일 스프레드시트**처럼 보여야 한다.
게임임을 드러내는 요소(하이라이트 애니메이션, 팝업, "승리!" 배너 등)는 쓰지 않고, 실제
스프레드시트가 이미 가진 UI 요소(공동편집 커서, 리본, 상태표시줄, 알림 토스트)를 그대로
게임 정보 전달에 재활용한다.

## UI 구성

- 상단 리본: 탭 라벨(홈/삽입/수식/데이터/검토 등)과 가짜 버튼 아이콘. 클릭 동작 없음, 장식용
- 우측 상단: 공동 편집자 아바타 2개(이니셜 원형). 현재 턴인 사람의 아바타에 강조 테두리
- 그리드: 50×50 셀. 열 헤더는 실제 스프레드시트처럼 A~Z, AA~AX(50번째 열)까지 이어짐
- 돌 표시: 셀 안에 문자 `●`(흑) / `○`(백)
- 상대방 마지막 착수: 해당 셀에 색 테두리 + 이름표(공동편집 커서 UI 재사용)
- 시트 탭 바(하단): 장식용 "Sheet1" 탭
- **오류/알림: 화면 우측 상단에 Excel 알림 토스트 스타일로 표시** (예: 자동저장/연결 오류 알림
  카드와 동일한 톤 — 흰 배경, 얇은 좌측 색상 바, 아이콘 + 짧은 문구, 수 초 후 자동 사라짐).
  게임임을 드러내는 문구(승리/패배 등)도 이 토스트로만 전달하고 모달은 쓰지 않는다.

## 시작 화면

- 닉네임 입력 (2~8자)
- 방 만들기 → 6자리 영숫자 코드 발급, 대기
- 방 참여하기 → 코드 입력 후 입장

## 게임 규칙

- 보드 50×50
- 렌주 금수규칙 적용: 3-3, 4-4, 장목(6목 이상) — **흑(선공)에게만** 적용
- 방을 만든 사람이 흑(선공)
- 5목을 먼저 만들면 승리
- 같은 방에서 재대전 지원: 보드만 초기화하고 흑/백 교대, 방 코드 재공유 불필요

## 기술 스택

- Next.js (App Router, 클라이언트 컴포넌트 위주) — Vercel에 정적/SPA로 배포, API 라우트 없음
- Firebase Realtime Database — 실시간 동기화, 별도 백엔드 코드 없음
- 상태 동기화는 Firebase SDK를 클라이언트에서 직접 구독(onValue)/기록(set, transaction)

## 데이터 모델 (Firebase RTDB)

```
/rooms/{roomCode}
  host:   { name: string, connected: boolean }
  guest:  { name: string, connected: boolean } | null
  turn:   "black" | "white"
  status: "waiting" | "playing" | "finished"
  winner: "black" | "white" | null
  lastMove: { row: number, col: number } | null
  board:  { "<row>_<col>": "black" | "white", ... }   // 착수된 칸만 저장 (희소)
```

- roomCode: 6자리 대문자+숫자 조합, 충돌 시 재생성
- board는 2500칸 전부가 아니라 착수된 칸만 key로 저장

## 핵심 로직

1. 셀 클릭 시 클라이언트에서 순서대로 검사
   - 내 턴인지 확인 → 아니면 토스트 "상대방 차례입니다"
   - 이미 돌이 있는 칸인지 확인 → 있으면 토스트 "이미 둔 자리입니다"
   - 흑 차례면 렌주 금수(3-3/4-4/장목) 검사 → 위반 시 토스트 "둘 수 없는 자리입니다"
2. 통과하면 board에 기록, lastMove 갱신, turn 전환, 5목이면 status/winner 갱신
3. 5목 판정과 금수 판정은 착수 지점 기준 4방향(가로/세로/대각선 2개) 스캔으로 계산하는 순수
   함수로 구현 (보드 크기와 무관하게 동작)
4. 서버 측 검증/치팅 방지는 두지 않는다 — 지인끼리 하는 캐주얼 게임이라 클라이언트 판정만으로
   충분하다고 판단

## 오류 처리 (전부 우측 상단 토스트)

- 존재하지 않는 방 코드 입력 → "방을 찾을 수 없습니다"
- 이미 host+guest가 다 찬 방에 3번째 인원이 입장 시도 → "이미 인원이 가득한 방입니다"
- Firebase 연결 끊김/재연결 → "연결이 끊겼습니다" / 재연결 시 자동 갱신
- 위 "핵심 로직" 1번의 착수 거부 사유들

## 재접속

- 방 코드로 다시 입장하면 Firebase에 저장된 현재 상태(board/turn/status)를 그대로 복원
- 새로고침해도 게임 진행 상태가 유지됨

## 범위 밖 (이번엔 하지 않음)

- 채팅 기능 (위장이 깨질 위험이 있고 요청도 없었음)
- 로그인/회원가입, 전적 기록
- 관전 모드, 3인 이상 대기열
- 서버 측 부정행위 방지

## 배포/설정 (사용자가 직접 수행)

- Firebase 프로젝트 생성 및 Realtime Database 활성화 → 프로젝트 config 값을 환경변수로 전달
- Vercel 프로젝트를 GitHub 리포지토리와 연결하여 배포
- Firebase RTDB 보안 규칙은 인증 없이 `/rooms/{roomCode}` 하위 read/write를 허용하는 단순한
  규칙으로 시작 (민감 정보 없는 캐주얼 게임이라는 전제, 추후 필요 시 강화)

## 테스트 방침

- 순수 함수(5목 판정, 렌주 금수 판정)는 유닛 테스트로 검증 (Vitest)
- 나머지는 브라우저 2개 창(호스트/게스트)을 띄워 수동으로 방 생성 → 입장 → 착수 → 금수 거부 →
  승리 판정 → 재대전 → 새로고침 후 상태 복원까지 한 사이클 검증
